## 2. Seed / data layer
- Seeds: catalog 1152, content 1954, orders 404, requests 249, tours 365 + tours/reviews 228, partners 126, reports 91, demo 64 lines; planner/data/places.ts 398, walking.ts 820 [M].
- demo/seed.ts createSeedState deep-clones (structuredClone) catalog/content/requests/partners/pickup seeds, so seeds are not mutated through state [M]. orders and tours come from factories. Good: one runtime source of truth (DemoState).
- Leaks around it [M]: `shop` imported straight from catalog/seed in 12 files (read-only constant, but a second source for shop data, not in DemoState); routes/lab.map.tsx uses `tourSeed` directly; `createTourSeed()` is called in 11 places as `state.data.tours ?? createTourSeed()` (use-tours.ts:45 even has a module-level `fallback`). Cause: DemoState.tours is optional (demo/types.ts:48) although upgradeDemoData always fills it. Result: every consumer carries a dead fallback and a second route to seed data; drift risk (stale fixture tours if tours missing).
- tours/lib/upgrade.ts merges stored tours over seed per id => seed changes silently re-shape user-edited tours, and "New or changed fixtures still appear only after Reset" (comment): DEMO_VERSION bump vs upgrade merge are two migration mechanisms.
- Planner data (places/walking) imported only inside features/planner [I from grep: walking.ts consumers in planner/lib]. Not duplicated with catalog.
