# 2.17 Trip answers per order or booking

Owner decision, 14 Oct 2026 (the coordinator's option 1). Worker report, 14 Oct 2026.

## 1. What was there and what changed

**Before.** The three optional trip questions (group or independent, arrival date, departure date; PRD §3, R09) were stored once per guest in `state.data.tripProfiles[guestId]`. Every answer overwrote the last. A skip only counted for requests sent before it. C07 and C13 showed the same `TripProfile` card. The account had a trip card on the Preferences screen ("Language and trip") and a "Trip profile answered/open" line on the hub row. C13 used the gift intro "Your answers don't change your pickup dates" on a tour.

**Now.**

- **Storage.** `Order.trip` and `TourBooking.trip` are an optional `TripRecord`: `travelStyle`, `arriveOn`, `leaveOn`, `answeredAt`, `skippedAt` (`features/checkout/types.ts`). `tripProfiles` is gone from `DemoData`. `upgradeDemoData` drops a stored `tripProfiles` map on load. Old per-guest answers are not moved onto orders, because nothing records which purchase they belonged to. `DEMO_VERSION` is unchanged.
- **Seed.** Anna's completed order SK-1012 (pickup 9 Oct) carries sample answers: on my own, 7–10 Oct, answered when she ordered. The dates are in the past, so they never pre-fill a new request or booking, and the existing drivers' flows are unchanged. As with every fixture change, a browser with stored demo data sees it after Reset.
- **Logic** (`features/checkout/lib/trip.ts`, new, pure):
  - `tripView(data, guestId, target)` returns the status (open, answered or skipped) and the answers the form starts with.
  - `withTrip(...)` writes one record to the target's orders or booking, for the signed-in guest's own purchases only.
  - The target is `{ kind: "gift", orderIds }` or `{ kind: "tour", bookingId }`.
- **Hook.** `useTripProfile(target)` (`checkout/hooks/use-trip-profile.ts`) replaces the per-guest hook. Save writes `{answers, answeredAt}` and Skip writes `{skippedAt}`, using the demo clock.
- **C07.** The target is the send's order ids from `?orders=`, after `useRequestSent`'s signed-in-guest filter. One answer is saved on every order from that send. `sentAt` was removed from `useRequestSent` because nothing uses it any more.
- **C13.** The target is the booking. The card uses the tour intro: "…don't change your tour date." / "…ändern nichts an Ihrem Tourdatum."
- **Pre-fill.** It applies when this purchase has no answers and another of the guest's orders or bookings has both an arrival and a departure date covering this purchase's day:
  - The day is the pickup date for gifts and the Zurich calendar day of `startsAt` for tours. The comparison is inclusive.
  - For a multi-order send, the trip must cover every order's pickup date.
  - If several trips qualify, the newest `answeredAt` wins.
  - Otherwise the form is blank. Pre-fill only sets the form's starting values; nothing is saved until Save.
- **C15 and C16.** A new "Your trip" / "Ihre Reise" section is the last block of the Overview tab (`checkout/components/trip-card.tsx`, new):
  - Answered: C15's fact rows (icon, small muted label, value) for the three answers. A footer line carries the flow note ("Your answers don't change the pickup date." / "…the tour date.") and an **Edit answers** button.
  - Not answered (open or skipped): one line ("Not answered yet. Your answers don't change the pickup date." / "…the tour date.") and **Answer now**.
  - Both buttons open the existing `TripProfile` questions (`TripFields`, split out of the form) in the app's bottom-sheet pattern. The arrival and departure date sheet nests inside it.
  - Save closes the sheet. Dismissing it saves nothing.
  - One button element serves both states, so focus returns to it after Save.
  - Gift copy never mentions the tour date, and tour copy never mentions pickup.
- **Edit scope.**
  - Orders carry no shared send or request id. They share `createdAt`, but that is a timestamp, not an id. **An edit on C15 applies to that order only.** The C07 card still saves to every order of the send.
  - An edit on C16 applies to that booking.
- **Account.** The trip card is removed from `ProfilePanel`. The hub row's trip half and `account.hub.trip.*` are removed. The Preferences row stays, since it is the only way to change language. Its title `account.section.profile` is now "Language" / "Sprache" (was "Language and trip" / "Sprache und Reise"). There was no `/account?tab=trip` route or C23 code, so nothing else needed removing. An unknown `?tab=trip` renders the hub.
- **i18n keys.**
  - Added (EN+DE): `tripProfile.introTour`, `tripCard.title`, `tripCard.open.gift|tour`, `tripCard.note.gift|tour`.
  - Removed: `account.hub.trip.answered`, `account.hub.trip.open`, `account.profile.trip.notAnswered`.
  - The `TripProfile` prop `skippedText` was removed with them; its only user was the account card.
  - Every remaining `tripProfile.*` key is still used.

**Reports (item 5).** No report or analytics code reads trip data. A grep of `front-end/src` for `.trip`, `travelStyle`, `arriveOn`, `leaveOn` and the trip hook finds only the C07/C13/C15/C16 UI and the seed. The `features/reports/` folder the Phase 5 session created at 12:45 holds only cost seed data and types. When segmentation is built, it should call `tripView` or read `order.trip` / `booking.trip` per transaction and count a transaction without answers as "undetermined"; the PRD and spec now say so.
