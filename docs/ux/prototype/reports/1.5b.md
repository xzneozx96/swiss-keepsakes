# 1.5b Shared confirmation dialog, used for removing a cart line (C04)

Owner request: "any delete action must come with a reusable confirmation dialog/modal first".

## 1. What I built

- **New `front-end/src/components/confirm-dialog.tsx`**, built on HeroUI v3 `AlertDialog` and following the design-system AlertDialog card. It has a soft brick danger icon, a heading, a one-sentence body, the ink destructive button (`variant="danger"`, already ink through `.button--danger`) and a tertiary Cancel. It has no close X, so Cancel is the first stop.
  - `ConfirmDialog` is a controlled component. Props: `isOpen`, `title`, `body`, `confirmLabel`, `cancelLabel?` (defaults to `confirm.cancel`), `tone?: "danger"` (the default), `onConfirm` and `onCancel`.
  - `useConfirm()` returns `{ confirm, dialog }`. The caller renders `dialog` once and calls `await confirm(options)`. It resolves `true` on confirm and `false` on Cancel, Esc, a backdrop tap or unmount. A second `confirm()` while one is open resolves the first as `false`. It needs no provider, so `__root` is untouched.
  - Behaviour:
    - Focus starts on Cancel, and Tab stays inside the dialog.
    - Esc and a backdrop tap cancel.
    - On phones it is a card anchored to the bottom, 16px from the edges. From `sm` it is centred, at size `sm` (384px).
    - On phones the buttons stack full width with the destructive one on top.
  - The JSDoc has usage examples for both forms. 1.13 can adopt it as it is.
- **Cart (C04): "Remove" now asks first.**
  - `CartLineView` gets `removeConfirm: ConfirmOptions`, built in `use-cart-view.ts`. `CartView` owns one `useConfirm()` and calls `line.onRemove()` only after the guest confirms.
  - Dialog text, EN: title "Remove Kapellbrücke pocket knife · Medium?"; body "1 × Kapellbrücke pocket knife · Medium · Engraving “Anna” (CHF 54.00) comes out of Order 1."; buttons "Remove from cart" and "Cancel".
  - Dialog text, DE: "Kapellbrücke Taschenmesser · Mittel entfernen?" / "… wird aus Bestellung 1 entfernt." / "Aus dem Warenkorb entfernen" and "Abbrechen".
  - After a confirmed remove, focus moves to the cart heading (`[data-cart-title]`, `tabIndex=-1`) instead of falling to `<body>`, so the next Tab lands on the next line's Remove. It is looked up after paint, so it also works when the last line goes and the route's empty state shows its own heading.
- **Quantity stepper: no change needed.** `QuantityStepper` defaults to `min=1`, and `useCart().setQuantity` clamps with `Math.max(1, …)`, so decreasing can never remove a line. Removing is only possible through "Remove".
- i18n (EN and DE): `confirm.cancel`, `cart.remove.title`, `cart.remove.body`, `cart.remove.confirm`.

## 4. Verification evidence

The Playwright MCP browser profile was in use by another worker, so per the brief I ran a headless Playwright script: `docs/ux/prototype/reports/1.5b-verify.cjs`, against `vite --port 5196`. The script seeds 3 cart lines (knife M with engraving "Anna", chocolate ×2, gift box), which group into 3 orders.

Results at 375px, the same in EN and DE:

- The dialog opens with focus on Cancel/Abbrechen. The card is 343px wide at x=16, and the page has no horizontal overflow.
- Cancel, Esc and a backdrop tap each close the dialog and keep the line ("4 gifts · 3 orders" unchanged). After Cancel, focus returns to the line's Remove button.
- Keyboard-only path: focus Remove, then Enter opens the dialog with focus on Cancel. Tab moves to "Remove from cart", and Tab again wraps back to Cancel (focus stays in the dialog). Tab to the confirm button, then Enter, removes the line. The cart re-groups to "3 gifts · 2 orders" (Order 1 to Order 2), and focus lands on the `h1`. The next Tab reaches the next line's Remove.
- Removing every line shows the empty state ("Your cart is empty." / "Ihr Warenkorb ist leer."), with focus on its `h1`. It is still there 1.5s later, so React Aria's focus restore does not steal it.
- DE showed no English key strings.
- The full script passed 3 runs in a row on an unchanged file, plus a 4th run with no console errors. The 1st of those 3 runs logged one console error: `useLocale must be used inside LocaleProvider` in `PrototypeBar`. The module URLs carried HMR `?t=` stamps, so I take it to be another worker's edit reloading the page mid-run, not this change.

Other widths:

- 1024px: centred, 384px wide, buttons side by side.
- 340px, DE: stacked, 260px buttons, no overflow.

Run note: one earlier run missed the EN keyboard confirm (the line stayed). That run started right after `confirm-dialog.tsx` had been rewritten and passed through `eslint --fix`. Every later run passed.
