# E1.9 Platform layer

## What changed

Request ids (first commit, owner decision from the E1.8 review)
- The server makes every request id. It goes into the logs, the `X-Request-Id` response header and `audit_log.request_id`. A sane inbound `X-Request-Id` (up to 255 of `[A-Za-z0-9_=-]`) is logged only as `clientRequestId`. Anything else is neither used nor logged. Hono's `requestId()` is gone, because it echoes the inbound id.
- The E1.8 echo tests were rewritten for the new rule and retagged `[E1.9]`.

Data shapes and migrations
- `api/src/platform/db/schema.ts`: `pgSchema('platform')` with `audit_log` (UUIDv7 id from Postgres 18's `uuidv7()`, `store_id`, `actor`, `entity`, `entity_id`, `action`, `before`, `after`, `reason`, `at`, `request_id`), `idempotency_keys` (primary key `(actor_id, key)`, `request_hash`, `response`, `expires_at`) and `webhook_events` (primary key `(provider, event_id)`, `received_at`, `processed_at`, `payload`).
- `api/migrations/0000_platform.sql` and `meta/`, generated by `pnpm --filter @sk/api db:generate` (drizzle-kit).
- `api/src/platform/db/migrate.ts` is the release command (`pnpm --filter @sk/api db:migrate`, or `node dist/platform/db/migrate.js`). It applies the SQL migrations, then installs pg-boss's schema, over `DATABASE_URL_UNPOOLED`. Running services start pg-boss with `migrate: false`, because section 5 says the runtime role runs no DDL.
- Config: `DATABASE_URL_UNPOOLED` is required in every role, the name `neon env pull` writes. Values are still never printed.

Ports and adapters (`api/src/platform/`)
- `db/client.ts`: the `pg` pool (5 s connect timeout, an `'error'` listener so a lost idle client cannot end the process), Drizzle over it, and the `Tx` type.
- `db/unit-of-work.ts`: `UnitOfWork<T>`, where `uow.run(async (tx) => ...)` wraps `db.transaction`. Use cases are generic over the transaction type, so they never import Drizzle. The test use case `makeRecordProbe` shows the shape.
- `audit.ts`: `AuditLog<T>`, with `record(tx, entry)`. `at` comes from the Clock.
- `jobs/queue.ts`: `JobQueue<T>`, with `send(tx, queue, data, { startAfter })` through `fromDrizzle(tx, sql)`.
- `jobs/boss.ts`: `startJobs` starts pg-boss on the direct connection in every role, because a send needs a started instance. Only `worker` and `all` supervise and run schedules. It replaces the E1.8 worker shell (`jobs/worker.ts` is deleted).
- `webhooks.ts`: `record(tx, event)` returns `'duplicate'` for a repeated `(provider, event_id)` and inserts nothing.
- `clock.ts`: `Clock { now(): Date }` and `systemClock`. The test adapter is `api/test/support/manual-clock.ts`.

Idempotency-Key (`platform/idempotency.ts` and `platform/http/idempotency.ts`)
- POST, PUT, PATCH and DELETE need the header. A missing or malformed key is a 400 with type `idempotency-key-required`. Keys are scoped by `(actor_id, key)`.
- The hash is sha256 over the method, path, query and raw body bytes.
- The claim joins the command's transaction. The middleware puts a pending claim in AsyncLocalStorage. The first statement of the request's first `uow.run` is `INSERT ... ON CONFLICT (actor_id, key) DO UPDATE ... WHERE expires_at <= now RETURNING`. It is race safe on the primary key, not check then insert.
  - When the command rolls back, the claim rolls back with it, so a retry runs again.
  - When the command commits, the claim commits too, so the command never runs twice.
- I chose this over one transaction around the whole request. Section 6.3 creates the PaymentIntent after the hold commits, and says a Stripe outage must leave the booking in place. A request-wide transaction would hold the departure `FOR UPDATE` lock during the Stripe call, and a Stripe failure would roll back the booking.
- After the handler, the full response (status, headers except `x-request-id`, `set-cookie` and `content-length`, and the body as text) is stored, whatever the status. It is replayed for 24 hours by the Clock, with `Idempotent-Replayed: true` and a fresh `X-Request-Id`.
- The same key with another method, path or body is a 422 with type `idempotency-key-reused`.
- In-flight case, decided and tested:
  - A second request that arrives before the first commits passes the first lookup. Its claim then waits on the primary key. When the first commits, the second rolls back before its work runs, and replays the first response. `onError` does not log this race as an error.
  - A repeat that finds the key committed but its response not yet stored polls for up to 1 s, then gets 409 `idempotency-key-in-use` with `Retry-After: 1`.
- A request that never opened a unit of work, such as a validation failure, stores nothing, so the corrected body runs with the same key. Stripe does the same: "If incoming parameters fail validation, or the request conflicts with another request that's executing concurrently, we don't save the idempotent result" (docs.stripe.com/api/idempotent_requests).
- If storing the response fails after the commit, the client still gets the real answer. The error is logged, and a repeat gets 409 until the key expires (last commit).
- The middleware is not mounted yet. See the open questions.

Health and main
- `/healthz` runs `select 1` on the pooled connection. It then reads this process's pg-boss row from pg-boss's instance registry (`getInstances()`, host and pid). The row counts as live while it is not stopped and has beaten within three 30 s heartbeats. Each check is bounded to 2 s. A failure is a 503 problem+json, type `unhealthy`, with `checks: { database, jobs }`. ROLE=worker still has no HTTP server.
- `main.ts` opens the pool, starts pg-boss, then starts the API. Shutdown runs in reverse: HTTP, then pg-boss (5 s timeout, under the 10 s hard exit), then the pool. pg-boss `'error'` events are logged.

Where the result differs from the architecture doc, the spikes or the brief
- D4 and `data-jobs-security.md` write `boss.send(..., { db: tx })`. pg-boss 12 needs an adapter, `{ db: fromDrizzle(tx, sql) }`, as SP2 used.
- Context7's Drizzle pages show the v1 beta migration layout (one folder per migration). drizzle-kit 0.31 writes `0000_platform.sql` plus `meta/_journal.json`, which the 0.45 migrator reads.
- SP2 let pg-boss migrate its schema at start. Here the release command does it, and services start with `migrate: false`.
- pg-boss 12 has no single "last heartbeat" value. Section 13's heartbeat check uses its instance registry (`getInstances()`, with `heartbeatOn` and `live`).
- Architecture 4.2 shows `ports.ts` per module declaring `JobQueue` and `Clock`, and `platform/clock.ts` holding the Clock port. The lint zones forbid an application file to import `platform/`, so each module's `ports.ts` will declare the same small shapes, and the platform adapters fit them structurally (noted in `backend/architecture.md`).
- The IETF draft writes the key as a quoted structured-field string. Only an unquoted key is accepted, which is what the SPA will send.
- Compose ran as `docker compose -p sk-e1-9 ...` so that `down -v` could not remove another session's `swiss-keepsakes` containers. The compose file is unchanged.

## Not verified

- Neon. Nothing ran against a Neon branch, pooled or direct. That includes Drizzle transactions through Neon's PgBouncer in transaction mode, and pg-boss over Neon's direct URL from this code (SP2 proved the latter in the spike only).
- A runtime role without DDL. Section 5's separate migration role does not exist yet. pg-boss maintenance (index rebuilds, `reindex` defaults to on) may need ownership of its indexes.
- A pg-boss upgrade that needs async migrations. The release command stops pg-boss right after `start()`, and services never migrate.
- Two machines, the Fly release command, and a container image. They belong to other stories.
- No job removes expired `idempotency_keys` rows. Section 8's `cleanup` job comes later. An expired key is free again, but the row stays.
- The live curl check ran before `ca407ca`. That commit only guards the response-store failure path, and an integration test covers it.
- Intermediate commits were not run one by one, only HEAD.
- The E1.8 process tests now run only in `pnpm test:integration`, and no CI runs that until E1.13.
- pg-boss sometimes emits a plain object, not an `Error`, on its `'error'` event. The E1.8 allow-list serializer logs that as `{"type":"object"}`, without a code.
- The health warnings are logged without the `requestId`.
- The front-end gates were not run separately, because `front-end/` is unchanged. The root typecheck, test and build cover it.

Open questions for the owner
- Mounting the idempotency middleware. It is built and tested but not mounted, because no command route exists yet and there is no actor until E2.2. Proposal: E2.2 mounts it on `/api/*` after the auth middleware, never on `/webhooks/*`. Which actor id should anonymous commands (D15 advice requests) use? A shared `anonymous` namespace relies on keys being random UUIDs.
- A 5xx after the commit is stored and replayed, so a committed command never runs twice. For E4, a route whose post-commit Stripe call fails should return section 6.3's retry state, not a 5xx.
- The hash covers the raw body bytes. The same JSON in another key order is a 422. The SPA must resend the identical body on a retry.
- A crash between the commit and storing the response leaves the key answering 409 for up to 24 hours. The command is never run twice.
- Use cases must let `IdempotencyKeyTaken` through and must not nest `uow.run`. The first committed unit of work in a request claims the key.
