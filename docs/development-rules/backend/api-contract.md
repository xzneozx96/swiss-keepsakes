# API contract

**Mostly design.** The `OpenAPIHono` app and the problem details are built (E1.8), and so are the `Idempotency-Key` middleware and webhook deduplication (E1.9) and the contract package with its diff gate (E1.10). The rest is not. Source: `docs/architecture/backend.md` D11, and sections 12 and 13. The front-end side of this contract is in `../frontend/api-integration.md`.

## Rules

- **REST with `@hono/zod-openapi`.** A route parses its request, calls a use case and maps the result. It holds no business logic. (D11)
  - Register every route with `app.openapi(createRoute(...))` inside `createApp` (or a function `createApp` calls), because `contractApp()` in `api/scripts/contract.ts` builds the document from that factory. A plain `app.get` or `app.post` is missing from the contract, and the `[E1.10]` route inventory test in `api/test/contract.test.ts` fails on it.
- **The Zod schemas in `packages/api-contract` are the single source.** The generated client is committed under `packages/api-contract/generated/`. CI fails if it differs from a fresh build. (D11)
  - Built: `packages/api-contract/src/` holds `problemSchema` and `healthSchema`, and the routes in `api/src/platform/http/app.ts` use them. A schema imports only `zod`. Give a schema that several routes share `.meta({ id })`, so the document names it once. Each id belongs to one schema object: reuse the object, never a second schema with the same id, because zod-to-openapi would silently point both at one component. Never name a schema with `.openapi(name)`. `generateContract()` fails on either.
  - After you change a route or a schema, run `pnpm contract:build` and commit `packages/api-contract/generated/`. It writes the app's OpenAPI 3.1 document (`openapi.json`, keys sorted) and the `openapi-typescript` types made from it (`schema.ts`). The generator is `generateContract()` in `api/scripts/contract.ts`.
  - The gate is `api/test/contract.test.ts` in `pnpm test`: it builds both files in memory and fails when the committed ones differ. No CI runs it yet (E1.13).
  - The client is `createApiClient(baseUrl)` in `packages/api-contract/src/client.ts`, `openapi-fetch` over the generated `paths`. It is written by hand, because the build rewrites everything in `generated/`. Add headers such as the Bearer token with `client.use(middleware)`.
  - The API runs the package from `dist/` in production: `pnpm build` and `pnpm --filter @sk/api build` compile it, and `pnpm --filter @sk/api start` passes `--conditions=sk-compiled` to Node. Plain Node cannot load the `.ts` source. Everything else (tsc, tsx, Vitest, Vite) reads the source. See `architecture.md` for the shape another package copies.
- **Errors are RFC 9457 problem details** with stable `type` codes. The front-end maps each `type` to translated copy. (D11)
  - Built: return `problem(c, { type, status, title })` from `api/src/platform/http/problem.ts`. It sends `application/problem+json` with `instance` (the path) and `requestId`. The codes in use are `not-found`, `validation-failed` (with an `errors` list of `in`, `path`, `message`), `internal-error`, `unhealthy` (503 from `/healthz`, with `checks`), `body-too-large` (413, over the 1 MiB limit `createApp` puts on `/api/*`) and the three idempotency codes below. They are the `problemTypes` list in `packages/api-contract/src/problem.ts`, and `problem()` accepts no other code and no status under 400, so add a new code there first. On the wire `type` is a plain string: a client maps each code in `problemTypes` to copy and shows generic copy for any other, so a page loaded before a new code still reads the problem (owner decision, E1.10 review). Every route spreads `problemResponses` from `api/src/platform/http/responses.ts` into its `responses`: a `default` response of `application/problem+json` with `problemSchema`, so the generated client types `error` as a problem for any status. A status with its own meaning, such as the 503 of `/healthz`, reuses `problemResponses.default` with its own description. Each success response carries `headers: requestIdHeader`, the `X-Request-Id` header component. `problem()` returns a typed response, so a route whose responses all declare content cannot return a status it does not declare. Other `HTTPException`s become `about:blank` with the status text and keep the headers of their `res`, such as `Retry-After` or `WWW-Authenticate`. A 5xx one is logged with its `cause`. Never put an exception's message in the body. Tests: `api/test/platform/http/app.test.ts`.
- **Lists use cursor pagination.** (D11)
- **Merchant edits send `If-Match`.** (D11)
- **Every state-changing request carries an `Idempotency-Key`.** The server stores it with a hash of the request and replays the answer for 24 hours. A reused key with a different body returns 422. (D11)
  - Built: `idempotency({ db, clock, actorId })` in `api/src/platform/http/idempotency.ts`, not mounted yet. Mount it on `/api/*` after the auth middleware (E2.2), never on `/webhooks/*`. The key is claimed inside the command's first `uow.run`, so do the command's writes in a unit of work, run a command's units one after the other, never at once, and let `IdempotencyKeyTaken` propagate. A claim waits at most 5 s on another request's open transaction. Codes: `idempotency-key-required` (400), `idempotency-key-reused` (422), `idempotency-key-in-use` (409 with `Retry-After`). A replay carries `Idempotent-Replayed: true`, the exact body bytes, and only these stored headers: `Content-Type`, `Content-Language`, `Location`, `ETag`, `Cache-Control`. Tests: `api/test/integration/idempotency.test.ts`.
- **Webhooks keep the raw body**, because signature checks need it. They are deduplicated in `webhook_events`. (D1, 4.2)
  - Built: `createWebhookEvents(clock).record(tx, event)` (`api/src/platform/webhooks.ts`) returns `'duplicate'` for a repeated `(provider, event_id)`. Queue the `provider-event` job in the same transaction.
- **Permissions are checked per role and per store.** A store route returns 403 to a member of another store. A partner response never contains email, phone, address, engraving or notes. (12)
- **The API verifies a Bearer JWT on every request** against the identity provider's JWKS, and checks the issuer. (13)
