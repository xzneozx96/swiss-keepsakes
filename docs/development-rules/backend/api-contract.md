# API contract

**Mostly design.** The `OpenAPIHono` app and the problem details are built (E1.8), the identity module's store, invitation and onboarding routes are the first routes of a module (E2.3, `api/src/modules/identity/adapters/routes.ts`, registered through `createApp`'s `CommandDeps.routes`), and so are the `Idempotency-Key` middleware and webhook deduplication (E1.9) and the contract package with its diff gate (E1.10). The rest is not. Source: `docs/architecture/backend.md` D11, and sections 12 and 13. The front-end side of this contract is in `../frontend/api-integration.md`.

## Rules

- **REST with `@hono/zod-openapi`.** A route parses its request, calls a use case and maps the result. It holds no business logic. (D11)
  - Register every route with `app.openapi(createRoute(...))` inside `createApp` (or a function `createApp` calls), because `contractApp()` in `api/scripts/contract.ts` builds the document from that factory. A plain `app.get` or `app.post` is missing from the contract, and the `[E1.10]` route inventory test in `api/test/contract.test.ts` fails on it.
  - `/api/auth/*` is the one mount outside the contract. Better Auth serves it (D8, built in E2.2), mounted with `app.all` in `createApp`, which the inventory test skips as it skips middleware. Its routes are not in `openapi.json`, so the generated client does not call them. It answers in Better Auth's own error shape (codes such as `OTP_EXPIRED` and `TOO_MANY_ATTEMPTS`), not problem details, and it takes no `Idempotency-Key`.
- **The Zod schemas in `packages/api-contract` are the single source.** The generated client is committed under `packages/api-contract/generated/`. CI fails if it differs from a fresh build. (D11)
  - Built: `packages/api-contract/src/` holds `problemSchema` and `healthSchema`, and the routes in `api/src/platform/http/app.ts` use them. A schema imports only `zod`. Give a schema that several routes share `.meta({ id })`, so the document names it once. Each id belongs to one schema object: reuse the object, never a second schema with the same id, because zod-to-openapi would silently point both at one component. Never name a schema with `.openapi(name)`. `generateContract()` fails on either.
  - After you change a route or a schema, run `pnpm contract:build` and commit `packages/api-contract/generated/`. It writes the app's OpenAPI 3.1 document (`openapi.json`, keys sorted) and the `openapi-typescript` types made from it (`schema.ts`). The generator is `generateContract()` in `api/scripts/contract.ts`.
  - The gate is `api/test/contract.test.ts` in `pnpm test`: it builds both files in memory and fails when the committed ones differ. CI runs it in the `gates` job.
  - The client is `createApiClient(baseUrl)` in `packages/api-contract/src/client.ts`, `openapi-fetch` over the generated `paths`. It is written by hand, because the build rewrites everything in `generated/`. The SPA calls the API on its own origin, so the browser sends the session cookie itself (D8). Send `Idempotency-Key` as a header of the call, with the key of the user's intent and not a new one per request: the stores client in `front-end/src/features/stores/api/api-client.ts` takes it from the screen's `useIdempotencyKey`, which reuses it for a retry after a timeout, a lost connection or a 5xx and renews it after a success or a final answer.
  - The API runs the package from `dist/` in production: `pnpm build` and `pnpm --filter @sk/api build` compile it, and `pnpm --filter @sk/api start` passes `--conditions=sk-compiled` to Node. Plain Node cannot load the `.ts` source. Everything else (tsc, tsx, Vitest, Vite) reads the source. See `architecture.md` for the shape another package copies, and for why a missing flag does not fail on Node 22.18 and later.
- **Errors are RFC 9457 problem details** with stable `type` codes. The front-end maps each `type` to translated copy. (D11)
  - Built: return `problem(c, { type, status, title })` from `api/src/platform/http/problem.ts`. It sends `application/problem+json` with `instance` (the path) and `requestId`. The codes in use are `not-found`, `validation-failed` (with an `errors` list of `in`, `path`, `message`), `internal-error`, `unhealthy` (503 from `/healthz`, with `checks`), `body-too-large` (413, over the 1 MiB limit `createApp` puts on `/api/*`), `unauthenticated` (401, a guarded route without a live session), `forbidden` (403, a signed-in actor that the guard of a store or admin route refuses), `origin-refused` (403, the Origin rule), the three idempotency codes below, and the store and invitation codes of E2.3: `store-slug-taken` (409), `invitation-not-found` (404), `invitation-expired` (410), `invitation-revoked` (410 at accept, 409 at resend), `invitation-super-admin` (403, a Super Admin cannot accept a store role), `owner-is-super-admin` (409, the Owner email of a new store belongs to a Super Admin), `invitation-already-accepted` (409), `invitation-email-mismatch` (403), `invitation-email-unverified` (403), `already-a-member` (409), `store-not-onboarding` (409), `onboarding-incomplete` (409), and the member codes of E2.4: `manager-is-super-admin` (409, the address of a Manager invitation belongs to a Super Admin), `invitation-already-open` (409, the address already holds an invitation for the store that is neither accepted nor revoked, an expired one included, so the Owner sends it again), `member-not-found` (404, also for a membership of another store) and `cannot-remove-owner` (409). The member routes also answer `already-a-member` (409, at invite and at resend), `invitation-not-found` (404, also for a row of another store), `invitation-already-accepted` and `invitation-revoked` (409 at resend and revoke), and `forbidden` (403, a Manager). An invitation problem never carries the invited email. They are the `problemTypes` list in `packages/api-contract/src/problem.ts`, and `problem()` accepts no other code and no status under 400, so add a new code there first. On the wire `type` is a plain string: a client maps each code in `problemTypes` to copy and shows generic copy for any other, so a page loaded before a new code still reads the problem (owner decision, E1.10 review). Every route spreads `problemResponses` from `api/src/platform/http/responses.ts` into its `responses`: a `default` response of `application/problem+json` with `problemSchema`, so the generated client types `error` as a problem for any status. A status with its own meaning, such as the 503 of `/healthz`, reuses `problemResponses.default` with its own description. Each success response carries `headers: requestIdHeader`, the `X-Request-Id` header component. `problem()` returns a typed response, so a route whose responses all declare content cannot return a status it does not declare. Other `HTTPException`s become `about:blank` with the status text and keep the headers of their `res`, such as `Retry-After` or `WWW-Authenticate`. A 5xx one is logged with its `cause`. Never put an exception's message in the body. Tests: `api/test/platform/http/app.test.ts`.
- **Lists use cursor pagination.** (D11)
- **Merchant edits send `If-Match`.** (D11)
- **Every state-changing request carries an `Idempotency-Key`.** The server stores it with a hash of the request and replays the answer for 24 hours. A reused key with a different body returns 422. (D11)
  - Built: `idempotency({ db, clock, actorId })` in `api/src/platform/http/idempotency.ts`, mounted by `createApp` since E2.3, the first command route (`CommandDeps.idempotency`, which `main.ts` fills). It sits on `/api/*` after the auth middleware and after the store, admin and `/api/me` guards, so an anonymous request or an outsider gets 401 or 403 before anyone asks for a key, and before the module routes that `CommandDeps.routes` register. Better Auth's `/api/auth/*` answers earlier and never reaches it, and `/webhooks/*` is outside `/api/`. `idempotencyActor` names who a key belongs to: the signed-in user, or one shared `anonymous` scope. The first anonymous command route (E6.3) must decide whether that scope is enough. A command's key is claimed inside the command's first `uow.run`, so do the command's writes in a unit of work, run a command's units one after the other, never at once, and let `IdempotencyKeyTaken` propagate. A claim waits at most 5 s on another request's open transaction. Codes: `idempotency-key-required` (400), `idempotency-key-reused` (422), `idempotency-key-in-use` (409 with `Retry-After`). A replay carries `Idempotent-Replayed: true`, the exact body bytes, and only these stored headers: `Content-Type`, `Content-Language`, `Location`, `ETag`, `Cache-Control`. Tests: `api/test/integration/idempotency.test.ts`.
- **Webhooks keep the raw body**, because signature checks need it. They are deduplicated in `webhook_events`. (D1, 4.2)
  - Built: `createWebhookEvents(clock).record(tx, event)` (`api/src/platform/webhooks.ts`) returns `'duplicate'` for a repeated `(provider, event_id)`. Queue the `provider-event` job in the same transaction.
- **Permissions are checked per role and per store.** A store route returns 403 to a member of another store. A partner response never contains email, phone, address, engraving or notes. (12)
- **The API reads the session from Better Auth on every request** (built in E2.2 as `authenticate` in `api/src/platform/http/authenticate.ts`, which sets the `actor` to `anonymous`, `guest`, `staff` (a role per store) or `super_admin`, creates the guest profile on the first authenticated call, and passes a renewed session cookie on. `GET /api/me` is the first guarded route, and `requireGuest` guards `/api/me/*`. E2.10 added the roles, read with the profile in one transaction from `store_memberships` and `platform_admins` on every signed-in request) with `auth.api.getSession({ headers })` and builds the actor from it. One rule checks `Origin` on every POST, PUT, PATCH and DELETE under `/api/`, `/api/auth/*` included, and never sees `/webhooks/stripe`, which is outside the `/api/` path prefix (built in E2.10 as `requireOwnOrigin`, see `data-jobs-security.md`). (D8, 9, 13)
- **Guard a route by its path, in `createApp`, before any handler.** `requireStoreMember` is mounted on `/api/store/:storeId/*` and `requireSuperAdmin` on `/api/admin/*` (E2.10, `api/src/platform/http/guards.ts`). A route under either prefix needs no guard of its own and cannot skip it. Register every `/api/store/*` route with `app.openapi` and a path that starts `/api/store/{storeId}`, because the generated permission matrix (`api/test/platform/http/store-guards.test.ts`) calls each operation of the document as an outsider and as the store's owner, and fails on a route that is missing from the document. A path parameter that names a store must not contain the word `store` outside `/api/store/{storeId}`, so the Super Admin's routes under `/api/admin/stores/{id}/...` call it `id`. A handler reads the store it acts in from `c.get('store')` (the verified lower-case id and the member's role), never from the raw path parameter, the body or the query. Use `can(actor, permission, { storeId })` from `@sk/domain/identity` for what a role may do inside a store. The matrix also fails on a route with a store id parameter outside `/api/store/{storeId}` (the public `/api/stores/{slug}/*` routes are allowed by design, architecture section 10).

## Not covered yet

`PATCH /api/store/{storeId}/information` sends no `If-Match` and answers no 412. The merchant edit rule above starts with E2.6.

The resend routes (`POST /api/admin/stores/{id}/owner-invitation/resend` and `POST /api/store/{storeId}/member-invitations/{invitationId}/resend`) take an optional body. An empty body is accepted with or without the JSON `Content-Type`. The middleware that allows it builds a new `Request` from the URL, the method and the headers, because the node server's request cannot be copied once its body is read (it answered 500 until E2.4 fixed that, and `identity-routes.test.ts` now calls it over a real HTTP server).

Route naming, versioning and rate-limit numbers are not written. They are in `docs/architecture/backend.md` section 10, which this file does not copy.
